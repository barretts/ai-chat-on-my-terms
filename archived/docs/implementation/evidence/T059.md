# T059 — Arena race and timing engine

Date: 2026-09-26. Feature IDs: AR-01, AR-02, AR-03, AR-04.

## Implemented behavior

`packages/arena/engine` provides `ArenaEngine` and `SQLiteArenaStore`.

- A race has one to four independent `ProviderPort` contestants. All contestants receive
  the same deeply frozen prompt, context, parameters, and feature settings. The connection
  and exact model IDs are captured before any stream starts. The engine never chooses a
  replacement provider or model.
- Each contestant has its own run ID, live text/reasoning output, capabilities, usage,
  monotonic timing, safe error, and terminal state. A failure or individual stop preserves
  that contestant's partial output and allows siblings to continue. Persisted contestants
  retain their input order for answer comparison.
- Requested tools, reasoning, JSON, and images require verified `yes` capabilities.
  Unknown support remains unknown. Embedded tool definitions require explicit permitted
  names, and embedded image payloads cannot bypass the vision gate.
- Defaults bound live output to 131,072 characters, reasoning to 65,536 characters,
  the shared snapshot to 262,144 bytes, received events to 20,000 per contestant,
  and execution to five minutes. Duplicate events count against the event limit.
  SQLite writes apply backpressure; there is no accumulating event or write buffer.
- The engine owns one race at a time, with at most four active stream resources.
  Optional `prepare(signal)` admits work through the host scheduler and acquires a model
  lease before request timing starts. Preparation can return the provider leased for that
  exact binding. The lease remains held until the provider iterator actually closes.
- `handle.done` settles after durable terminal results. `handle.resourcesDrained` settles
  after stream and preparation resources close. A provider that ignores stop cannot free
  its slot or model lease early; a second race waits for actual resource drainage.
- `recover()` marks persisted nonterminal contestants and races interrupted, retains
  partial answers/timing, and advances their HLC revisions. It does not resend requests.
  Restarting an interrupted race requires an explicit new race.

## Timing labels

Entity timestamps and revisions use wall time; latency measurements use `performance.now()`
or an injected monotonic clock. TTFT measures from provider request admission to the first
nonempty generated text or reasoning delta. Download/load performed in preparation is
recorded as `preparationMs` and excluded from request latency.

The following fields have different meanings and are persisted separately:

| Field | Source |
| --- | --- |
| `providerReportedTokensPerSecond` | Explicit backend decode telemetry supplied by `readReportedMetrics`; null when unavailable |
| `providerOutputTokens` / `providerInputTokens` | Normalized provider `Usage` events |
| `reportedTokenCountPerSecond` | Provider output count divided by backend decode duration when reported, otherwise the observed output interval |
| `estimatedOutputTokens` / `estimatedTokensPerSecond` | Explicitly labeled token estimate; default is generated characters divided by four |
| `decodeMs` / `decodeTimingSource` | Reported backend decode duration, or first generated output through terminal observation |

The observed output interval excludes initial download/load/prompt work and includes
transport and persistence overhead. It is not a backend decode measurement. The current
normalized `RunEvent.Usage` contract does not carry backend rates or decode duration, so
these are never inferred and labeled provider reported. Host adapters may supply explicit
backend telemetry through `readReportedMetrics`.

## Persistence and migration handoff

`ARENA_SQL` in `src/sqlite-store.ts` is a static additive SQL migration proposal. It creates
`arena_runs` and `arena_contestants`, including exact binding columns, checked JSON records,
stable UUIDv7 identities, creation/update timestamps, and HLC revision columns. Existing
`arena_sessions` rows remain untouched. The root coordinator owns version allocation and
registration in the shared migration runner.

The snapshot, every contestant, live partial output, final result/failure, and timing are
stored in real SQLite. Connection objects, resolved headers, and credentials are retained
only in memory. Secret parameter fields are rejected before a race is stored. Provider
failures become bounded messages with typed codes before persistence; raw error bodies and
thrown messages are not copied into records.

The fake-clock check proves 5,000 ms of preparation plus 1,000 ms of stream load do not
enter a 200 ms observed output interval. It verifies a 1,300 ms TTFT, reported token-count
rate, separate character estimate, explicit backend-rate telemetry, and a backwards wall
clock adjustment.

The actual HTTP fixture starts a localhost server and uses the production Ollama chat port
and HTTP transport with explicit authorized/cleartext origins. Four exact model requests
reach the server before responses are released. Three fragmented NDJSON answers complete;
one returns HTTP 401. All four results, usage, and bindings persist, live updates retain
contestant identity, and the raw error body is absent from stored results.

Additional checks cover frozen shared settings, duplicate suppression, unknown capability
gates, cross-run event rejection, missing terminal events, bounded output and duplicate-event
floods, individual stop, timeout isolation, late preparation cleanup, uncooperative stop,
file-backed reopen, interruption recovery/HLC advancement, and legacy session preservation.
