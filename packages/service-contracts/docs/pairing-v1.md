# Pairing and relay v1 wire contract

The QR payload is a short-lived bootstrap object containing a random route ticket and a generated 256-bit pairing secret. The relay receives the route ticket hash only; it never receives the pairing secret. A peer hello proves secret possession and binds the protocol version, route, and roles into HKDF-SHA256 input. Fresh salts and nonces derive directional AES-256-GCM keys for each session. Counters are per direction, and receivers reject replayed or out-of-window counters.

The relay sees only opaque frames and routing metadata. It applies the one MiB frame limit, expiration, route allowlist, and byte limits. Binary transfers use bounded chunks and verify the declared length and SHA-256 after reassembly. The relay stores no message history. Sync payloads move only explicitly opted-in records and blobs; API keys, provider headers, pairing secrets, PINs, and model files are excluded.

The current wire version is **1.2** (`PAIRING_PROTOCOL`). `assertProtocolCompatible` rejects a peer with another major version or a minor above its own local minor before encrypted application traffic starts, and the remote crypto channel stamps every payload with the exact `${major}.${minor}` label, rejecting a handshake whose version is not identical — so live pairing peers must run the same minor build. The handshake itself travels only in sealed envelopes over a random-nonce channel carrying possession proofs plus a fresh per-connection ephemeral salt each way; both sides then derive fresh directional AES-256-GCM data keys and replay windows for every connection, so a saved pairing can never reuse a (key, nonce) pair across sessions, and frames from an earlier session fail authentication. Stale or superseded QR text is rejected by the strict QrV1 schema and relay-ticket binding, which surfaces as a re-pair prompt rather than a silent fallback.
