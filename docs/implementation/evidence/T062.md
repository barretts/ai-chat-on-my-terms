# T062 - Tool registry and bounded execution loop

Date: 2026-09-26. Features: TL-01, TL-09.

## Implemented behavior

- `ToolRegistry` stores enabled tools with an object schema, argument parser, executor,
  and UUIDv7 server identity. Global, chat, and participant switches resolve once per run.
  Registry and policy edits affect the next run. Unknown or denied tool capabilities
  produce no tool schemas or permitted tool names.
- `ToolLoopEngine` preserves explicit provider/model/conversation binding across provider
  rounds and emits one aggregate run with strictly ordered events and participant identity.
  It retains partial text/reasoning, executes permitted parsed calls, appends structured
  assistant/tool exchanges, and continues to the terminal assistant answer.
- The default round limit is eight. Explicit unlimited rounds retain deadlines and resource
  budgets. Defaults include 128 calls, 256,000 generated characters, 64,000 argument bytes,
  128,000 result bytes, 4,000,000 request/context bytes, 256 KiB per event, 20,000 events,
  and 4 MiB total emitted bytes. Event bytes can be configured up to 1 MiB and total bytes
  up to 32 MiB. A reserved terminal allowance ensures a safe quota event fits when the
  aggregate budget fills. Definitions, parameters, transformed arguments, saved results,
  progress detail, and source metadata are covered by their corresponding limits.
- Generation defaults to a 60-second deadline, configurable up to five minutes. Async
  policy setup has its own 60-second limit and responds to parent cancellation. Provider
  and executor waits race the loop's abort signal. Closing immediately after `RunStarted`
  clears the timer/listener before a provider is started.
- `SQLiteToolInvocationStore` persists UUIDv7/HLC invocation records. Replay binding
  includes conversation, run, server, tool, parsed input, and participant, including an
  omitted participant. Atomic `claimExecution` moves pending work to running once;
  concurrent losers cannot execute or cancel another loop's claimed work. `finish` accepts
  terminal states only and cannot reset claimed work to pending. Completed results are
  reused; reopening marks unfinished work interrupted without automatic side-effect retry.
- Invocation writes use the explicit SQLite transaction facade for binding reads, atomic
  claims, terminal updates, and revision allocation. Legacy adapters that call the
  callback without a facade remain supported.
- Tool schemas and injected function controls are removed when unsupported. The Ollama
  adapter excludes definition entries from messages and forwards only schemas with a
  string function name present in `permittedTools`.
- Failures use safe typed messages. Executor/provider error bodies do not enter durable
  invocation error records or aggregate failure events.

## Local checks

These are deterministic Windows fixtures and file-backed SQLite checks. Ollama tests use
the actual HTTP adapter with injected fixture responses; no live Ollama server or paid
provider is claimed.

Regression checks cover concurrent pending claims, losing-loop cleanup, speaker mismatch,
nonterminal reset rejection, cancellation after begin commits, early closure, async-policy
cancel/deadline, frozen policy, malformed switches, metadata/event-count/aggregate-byte
limits, schema/parameter/transformed-input bounds, partial output, eight-round and unlimited
limits, safe executor failures, durable reopen, and real adapter replay framing.

The final file-backed regression imports the actual app `sharedMobileDatabase` facade.
An unrelated transaction temporarily changes an invocation and rolls back. A concurrent
claim and ordinary audit write wait; the claim sees restored pending work and succeeds
once, the audit write persists, and a second claim cannot acquire the running invocation.

## Integration and remaining proof

- The coordinator registers `TOOL_ENGINE_SQL` through the app migration runner and mounts
  tool settings/registry/provider wrapping. The review fixes do not change the DDL.
- Supply the app's UUIDv7 generator as `createId`; the package's default generator requires
  `crypto.getRandomValues`. Every custom invocation store must implement atomic
  `claimExecution(id)` and terminal-only `finish`.
- T063-T069 supply actual search, browser, MCP, sandbox, server, and UI integrations;
  this card supplies their registry/execution boundary. Tool executors must honor their
  provided abort signal to stop their own external work.
- T070 composes the full tools feature. Physical iPhone, real provider/tool services,
  permission prompts, active tool cancellation, and platform-specific recovery remain
  pending under the later device/service verification cards.
